# Reachability floors: the share of program locations each harness reaches
# at its configured bound, measured by `cbmc --cover location` under the
# same --unwind, --unwindset and -D flags its launch line proves under.
# The numbers are the nightly runner's (ubuntu, the pinned cbmc): a
# macOS build of the same harness carries a few more or fewer locations
# in its goto model, so a floor measured there can sit a few tenths of
# a percent off the runner's reading. Record what the nightly's own
# table prints, not a local measurement.
# proof/coverage.py builds that command from proof/run.sh: the launch
# line's own sources and flags, then the -D flags launch() adds to that
# harness. Those are -DCH_RAND_EXTERN, and -DCH_NATIVE_WIDEMUL for each
# harness outside a host object, whose launch line does not pass
# -DCH_CPU_RUNTIME. `python3 -u proof/coverage.py --reach --only NAME`
# measures one harness that way and prints the command it ran, so a
# floor recorded by hand and the nightly's number come from one command.
# From 6552715, which added -DCH_NATIVE_WIDEMUL to launch(), until
# https://github.com/c4milo/chapulin/issues/113 the cover command left
# that define out, so the nightly measured poly1305 on ct.h's 16x16
# decomposition and held it to a floor recorded on the native multiply
# its proof compiles. `--cover location` counts basic blocks, and each
# form of ct_widemul is one block, so poly1305 measured 149 of 158
# (94.3%) under both commands on 2026-09-02: the fix moved the command,
# not a floor.
#
# The define dropped out a second time. 82a1e071 moved it from launch()'s
# args to its widemul_def on 2026-10-03, and proof/coverage.py read args
# alone until 2026-10-17. Without the define, seven x25519 harnesses
# counted one more location of ct.h's 16x16 decomposition, and reached
# one or two more. Run 39059024456 read x25519_tail at 52.6% (110/209)
# that way. With the define, run 39075335784 read 52.2% (108/207), the
# floor that bea733df recorded under the define. No other count moved:
# for every other harness that both runs measured, they printed the same
# number.
#
# The cover command also passes --slice-formula, as run.sh does for every
# proof. Until 2026-10-01 it did not, so a cover formula kept every value
# a harness computes and no goal reads, such as the bytes a builder
# copies into its output, and hello_build_suite's formula needed more
# memory than the runner has (https://github.com/c4milo/chapulin/issues/163).
# The slicer drops only those values, so no count moved. In an ubuntu
# 24.04 amd64 container with the pinned cbmc, the sliced command printed
# the last nightly's number for 89 of the 117 harnesses outside the
# no-floor list. Of the other 28, 4 were new, and 24 had sources that
# changed after that nightly; for each of those 24 the sliced and
# unsliced commands gave the same count. That fix also moved the command,
# not a floor.
#
# Why a floor rather than a threshold: a harness that stubs its dependencies
# legitimately reaches less of its translation unit than one that compiles
# them concretely, so there is no single number that is right for all of
# them. What is always wrong is a harness reaching less than it used to,
# because that means a bound shrank below the code the harness names and the
# proof still reports success. That is the failure this file exists to
# catch, and it is not hypothetical: 7206f4c and 93e9504 both shipped
# proofs that passed while proving less than they claimed.
#
# One "name percent" line per harness, and an optional budget=SECONDS field
# for a harness whose cover run needs longer than proof/coverage.py's
# REACH_BUDGET_S. An optional solver=cadical field names the SAT solver of
# a harness whose cover run does not converge on cbmc's default solver,
# MiniSat 2. REACH_SOLVERS in proof/coverage.py says why the field exists
# and why CaDiCaL is not the default. An optional object_bits=N field
# gives the cover command --object-bits N, for a harness whose cover run
# stops on cbmc's "too many addressed objects" while its proof does not.
# proof/coverage.py says why that field changes no count. A harness
# absent from this file is measured and reported but carries no floor;
# the nightly publishes the table, so adding a line is a matter of
# copying the number it printed.
# The table is on the run page of the nightly's merge-reach-table job,
# which joins the parts that the three proof-reach jobs measure.
# Lower a floor only with the reason in the commit body.
#
# See https://github.com/c4milo/chapulin/issues/55.

# No floor, because `cbmc --cover location` does not converge on them.
# This is a limit of the measurement, not a gap someone forgot: the
# same solver cost that makes the proof slow makes counting its
# reachable locations slow. proof/coverage.py reads this block and
# skips them: running them anyway cost the nightly its runner (a cover
# formula grew past the VM's memory on 2026-09-02 and the job died
# without a log). Re-measure one by hand: `--only NAME` runs a harness
# named here under the cover command and REACH_BUDGET_S, and the command
# it prints runs under any budget. Move it to the roster above when it
# converges. Each got five minutes a harness, except handshake_pin and
# handshake_psk, which got ninety minutes each, under the command
# proof/coverage.py passed before
# https://github.com/c4milo/chapulin/issues/113 (cbmc 6.11.0, built-in
# solver, no -DCH_NATIVE_WIDEMUL). Of this block only mlkem_poly compiles
# a ct_widemul-family function, so that define changes its formula
# alone. Every measurement in this block was taken without
# --slice-formula, which the cover command has passed since 2026-10-01.
# Slicing changes no count, and it took hello_build_suite's cover run
# from more than 13 GB to 0.13 GB, so a harness here may converge now:
# measure it before you move it, and record what the nightly prints.
# handshake_pin and handshake_psk were still in propositional reduction
# when the budget killed them, at 8.3 GB and 7.4 GB peak RSS.
# proof/coverage.py stops a harness at REACH_BUDGET_S, so the nightly
# reports both as timed out. hkdf_expand and hkdf_expand_label converge (60.0%
# and 81.2% on 2026-09-02, about 520 s each) but at 16 GB of memory,

#
# The four TRANSPORT=quic-nonblocking harnesses are listed from one measurement and
# one inference, and the inference is why they are here rather than in
# the roster. The aes harness returned no usable number under the cover
# command on a development machine on 2026-09-18 (arm64 macOS, the pinned
# cbmc, about 21 minutes, 0.6 GB peak) -- and its proof takes 23 s, so
# cover costs it more than fifty times what proving it costs. gcm_refusal
# was still running when the 1500 s cap on that whole session stopped it;
# gcm_safety and ghash were not reached. Their proofs take 282 s,
# 52 s and 274 s, all above the aes harness's 23 s, so nothing suggests
# their cover formulas do better than the one that already failed. Listing all

# Measure one by hand with `--only NAME` and move it to the roster above
# when it converges.
#
# mlkem_ntt, mlkem_invntt_low and mlkem_invntt_high timed out in all five
# nightly runs whose logs remain (33686419744, 33691163738, 33715874614,
# 33717153636, 33731054741), and the three of them took 45 minutes of
# every one of those runs. They carry no floor, so each timeout failed
# nothing. mlkem_ntt returned no verdict in 1800 s either, under the
# cover command on a development machine on 2026-09-03 (cbmc 6.11.0,
# 6.3 GB at the cap). That machine runs hello_build's cover in 190 s
# against the runner's 280, so 1800 s there buys more solver time than
# 1800 s on the runner would. The other two are the same butterfly over
# the other half of the transform. Their proofs are unaffected: run.sh
# proves all three, and prove-slow reports the three of them green.
#
# pem and pem_ecdsa timed out in those same five runs, at a budget below
# what they need rather than because they do not converge. Under
# REACH_BUDGET_S they do: run 33888303774 measured pem at 74.6% in 1665 s
# and pem_ecdsa at 74.6% in 1503 s, and both carry floors above.
#
# Their runner times also correct a wrong inference. pem takes 1654 s on a
# development machine and 1665 s on the runner, a ratio of 1.01, while
# hello_build takes 186 s there and 310 s here, a ratio of 1.67. The two
# machines do not differ by one factor. hello_build peaks at 12.2 GB
